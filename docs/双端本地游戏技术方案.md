# 旅行养成小游戏 · 双端本地游戏技术方案

版本：v0.1｜日期：2026-11-12｜状态：技术选型与实施规划，尚未实现双端打包

## 1. 目标与范围

交付可下载安装的 Windows PC 游戏与 Android APK。两端共用游戏规则、内容配置和主要界面，断网也能完成采集、购买、装包、旅行、领取与图鉴收集。玩家数据保存在本机，核心玩法不依赖账号、自建服务器或第三方接口。

PC 首版指 Windows；macOS、Linux 和 iOS 不在首版交付范围。浏览器版保留为开发预览和轻量试玩入口。微信仅用于可选的单向事件摘要推送，不接收玩家发给微信的消息。

本方案补充并更新 [MVP 产品设计](./MVP产品设计.md) 的交付平台与通知范围。当前浏览器预览是流程和画面原型，不能视为已经具备安装包、原生存档或微信推送。

## 2. 技术选型

| 层次 | 选型 | 用途与边界 |
| --- | --- | --- |
| 共用前端 | Vite + TypeScript + 原生 HTML/CSS | 场景、弹窗、输入与构建；首版不引入大型 UI 框架 |
| 游戏核心 | 独立 TypeScript 模块 | 状态机、经济、旅行、随机结果与离线结算，不引用 DOM 或平台 API |
| 美术与声音 | WebP、SVG、精灵图、MP3 | 所有必要资源随安装包分发；CSS 与 JavaScript 驱动轻量动画 |
| Windows 容器 | Electron + Electron Forge | 本地资源加载、系统文件与通知、Windows 安装包 |
| Android 容器 | Capacitor + Android 原生工程 | 本地 WebView、生命周期、存储、通知与 APK 构建 |
| 持久化 | 统一 JSON 格式 + 平台存储适配 | PC 写入用户数据目录；Android 使用 Preferences；浏览器使用 localStorage |
| 可选推送 | 独立 HTTPS 通知适配器 | 用户自行配置推送服务，先做渠道验证，不绑定游戏核心 |
| 自动化验证 | Node.js 测试、Python unittest、TypeScript 检查 | 复用现有测试，后续补充平台适配与打包验证 |

选择 Electron 是为了复用网页代码并使用随包附带的 Chromium，代价是安装体积与内存占用较大。当前场景以固定插画、少量动画和点击物品为主，暂不需要物理引擎。若后续出现大量实时精灵、复杂镜头或性能瓶颈，再通过真机测量决定是否引入 Canvas 渲染。

具体依赖版本在工程化阶段按当时兼容矩阵选定并写入锁文件，记录 Node.js、Electron、Capacitor、JDK、Android SDK 和构建工具版本。Android 最低系统版本由选定 Capacitor 主版本及真机验证共同确定，不能提前承诺任意旧设备可用。

## 3. 模块与平台边界

建议后续目录如下，本次文档交付不创建这些工程目录：

```text
src/
  core/              游戏状态、命令、旅行与离线结算
  content/           物品、目的地、明信片、事件与平衡配置
  ui/                家园、弹窗、输入、动画与音效
  platform/          存储、文件、时钟、通知、凭证与生命周期接口
  notifications/     摘要生成、发送队列、渠道适配
desktop/             Electron 主进程、preload 与打包配置
android/             Capacitor 生成并维护的 Android 原生工程
tests/               核心、适配契约、迁移与界面测试
```

界面发出命令，核心校验并产生新状态及事件，持久化协调层保存成功后才确认操作。所有写入串行化，避免快速点击、后台切换和发送队列更新相互覆盖。

平台层提供 SaveStore（读写及恢复）、FileTransfer（导入导出）、Clock（时间）、LocalNotifier（本机通知）、CredentialStore（推送凭证）、MessageSender（联网发送）和 Lifecycle（前后台事件）接口。核心只依赖传入的数据、时间和随机源，不直接调用 Electron、Capacitor、fetch 或 localStorage。

Windows 使用单实例限制并聚焦已有窗口，避免两个进程同时写同一存档。Android 原生插件仅在平台层调用。浏览器存储不可用时可以临时试玩，但必须明确提示进度无法持久保存。

## 4. 游戏状态与事件

延续现有状态流转：在家 → 准备好 → 旅行中 → 归来待领取 → 在家。旅行包含独立 tripId、准备时间、出发时间、归来时间、消耗物品、目的地、固定奖励和途中事件。

确认行李时一次性确定并保存该趟旅行的随机结果与事件时间线，避免刷新、重启或改设备后重新抽取结果。重开时按时间暴露已发生的事件；首次奖励、物品消耗与领取均有持久化标记。

归来和领取分开：归来只使奖励可领取；领取命令在同一次存档提交中增加图鉴并标记已领取。同一 tripId 重复领取不产生第二份奖励。保存失败时保留此前有效进度并提示重试，不能只在界面中显示领取成功。

每个事件使用稳定 eventId，例如 tripId 加事件序号，并保存 occurredAt、type 与内容参数。首版只保留最近 100 条旅途事件；图鉴获得次数独立累计，不因裁剪历史而丢失。

## 5. 本地存档与跨端转移

两端共用带版本的 JSON 数据协议。以下为协议示意，正式字段以实现时的类型定义和校验器为准，不能直接当作现有 Demo 存档导入：

```json
{
  "format": "traveling-feiyv-save",
  "schemaVersion": 1,
  "contentVersion": 1,
  "revision": 1,
  "savedAt": 1794441600000,
  "lastSettledAt": 1794441600000,
  "state": {
    "coins": 80,
    "inventory": { "rice": 2, "map": 1 },
    "status": "home",
    "trip": null,
    "album": {},
    "introGranted": true
  },
  "events": []
}
```

schemaVersion 管理数据结构迁移，contentVersion 对应内容配置，revision 用于本机排序。时间统一为 UTC 毫秒时间戳，显示时才转为设备时区；物品与明信片使用稳定 ID。金币、数量、时间范围、状态与引用关系必须在读取时校验，不能只验证 JSON 能否解析。

Windows 在 Electron 用户数据目录写主存档和上一份有效备份：先写临时文件并完成刷盘，再替换主文件。Android 初期存档较小，Preferences 使用两个槽位保存带 revision 和校验摘要的快照，读取时选择校验通过且版本兼容的最新快照，写完读回验证；不假设多次键写入构成事务。若内容规模增长，再评估 SQLite。

校验摘要只用于发现意外损坏，不提供防作弊能力。升级遇到未知高版本时拒绝覆盖并允许导出原文件；主存档损坏时尝试备份恢复，恢复失败也不静默重置。购买、采集、装包、领取和设置变更后及时保存，不依赖退出回调才保存。

跨端通过“导出存档 → 传输文件 → 导入存档”实现，首版不做自动同步或合并。导入限制文件大小为 2 MiB，校验后显示进度摘要，经用户确认并备份当前存档后完整替换。首次不兼容内容 ID 必须明确处理，不能静默删除收藏。

导出只包含游戏进度与跨端通用设置，不包含推送 Token、设备专用配置或发送队列。导入后重新安排本机通知，并从当前事件位置建立推送起点，历史事件不自动重发。卸载、清除应用数据或设备损坏可能丢失本地存档，导出功能作为手动备份入口。

浏览器 Demo 的 localStorage 不会自动出现在 Electron 或 APK 中；后续提供显式的 Demo 存档迁移入口和转换测试。离线存档可复制，两个分支进度只能择一导入。

## 6. 离线推进与时间处理

应用启动、恢复前台和玩家操作前执行 settle(state, now)。准备和旅行状态根据固定时间线推进；即使跨过多个阶段也应一次结算到正确状态。关闭期间不会自动开始第二趟旅行，钱草最多成熟一轮，避免无限累积收益。

不要求进程常驻。旅行期间记录时间与结果，重新打开后补算即可。多次以相同 now 调用结算应得到相同结果，不重复发奖励或创建事件。

首版采用本机时间。设备时间回拨时使用 max(now, lastSettledAt) 作为结算时间，避免状态倒退；大幅向前调时可能提前结束旅行，接受这一单机限制。时区变化不影响 UTC 时间差。界面倒计时只负责展示，不能成为奖励发放依据。

## 7. 画面、输入与生命周期

保留开放式小屋、庭院和物品入口。桌面支持鼠标、键盘焦点、窗口缩放与最小窗口尺寸；安卓优先竖屏、触屏和系统安全区域，主入口至少 44×44 CSS 像素。对窄屏重新排布场景，不能只把桌面画面整体缩小。

安卓返回键先关闭顶层弹窗，再由主场景处理退出；退出不清空存档。切到后台时暂停无意义动画和声音，尽力保存已提交状态；恢复时结算进度并刷新通知。保存仍以每次关键操作为准，因为系统可能直接终止进程。

WebP 背景、角色分层和精灵动画承担主要画面，SVG 用于小图标和适合矢量绘制的物品。美术、字体、音频均随包提供并记录来源和授权；不引用参考游戏的素材。首轮在目标安卓真机测量首屏耗时、图片解码、内存和交互卡顿，再确定资源尺寸预算。

## 8. 微信单向推送

微信是可关闭的扩展功能，默认不启用。先用固定模板把已发生事件汇总为短消息，例如“今天去了月牙湖，遇见一只小螃蟹，带回一张明信片”。首版不接 AI，不接收微信消息，也不要求注册游戏账号。

首选验证用户自备推送凭证的第三方渠道，PushPlus 仅作为候选。接入前验证实际微信到达、账号绑定、额度、内容限制、HTTPS 接口及服务条款；验证通过后才列为支持渠道。HTTP 请求成功或服务受理不等于微信已送达，界面据实际响应显示“已提交”或失败原因，不虚报送达。

发送入口为玩家主动发送、游戏运行时归来触发，以及重新打开后补发离线摘要。联网调用通过平台适配层完成，避免浏览器跨域策略与 APK 行为不一致。核心玩法不等待网络完成；断网或渠道不可用也不回滚奖励。

发送队列单独持久化于本设备，记录 messageId、事件范围、摘要、尝试次数、下次尝试时间和提交结果。自动摘要按 10 分钟窗口合并，每天最多 3 条，每条至多自动尝试 3 次；配额或授权错误暂停并提示用户处理，离线时不消耗重试次数。超时视为提交结果未知；渠道没有幂等键能力时由用户选择是否重试，不无限自动重发。停用推送后取消未发任务。

持久化后再发网络请求，并使用稳定 messageId 防止本机重复入队。外部接口受理后若本地写回失败，仍可能发生重复，首版不承诺跨服务的严格恰好一次。保存最近 100 条提交记录用于排查，不记录完整凭证。导入存档不恢复另一台设备的通知队列。

凭证由用户输入并保存在设备凭证存储中，不能放入源码、安装包公共配置、日志或导出存档。Electron 使用系统支持的安全存储；Android 使用基于 Keystore 的插件或小型原生实现。普通 Preferences 不是加密凭证仓库；凭证安全存储不可用时禁用持久记忆或仅在当前会话使用，不静默明文回退。凭证可查看绑定状态、替换和删除。

不开自建服务器不等于微信推送完全离线：发送时需要网络，并依赖第三方服务。手机关机、应用被强制停止或 PC 已退出时，首版不承诺定时发送微信。若未来必须实现此能力，再增加只负责定时通知的云端服务，并另行设计上传数据范围和用户授权；无需因此迁移全部本地存档。

## 9. 本机通知与后台限制

本机通知与微信推送是两条独立渠道。安卓通过 Capacitor Local Notifications 预先安排归来提醒，Windows 可在进程运行时发系统通知。拒绝通知权限时游戏照常运行。修改旅行、重新开始或导入存档后取消旧提醒，再按当前状态安排，通知 ID 与 tripId 关联。

安卓需要按系统版本申请通知权限，提醒时间受系统调度、省电设置和厂商策略影响。首版接受非精确提醒，不把精确闹钟或常驻前台服务作为默认前提。Windows 首版不做退出后的常驻托盘与开机自启；不保证退出后提醒。

通知正文只做提醒，点击后启动或聚焦游戏并重新结算，不能直接发放奖励。应用无需长期后台运行即可推进离线进度，但不能由此推导出关闭后仍能执行网络发送。

## 10. 安全与本地权限

Electron 使用 contextIsolation、sandbox 并关闭 nodeIntegration，通过 preload 暴露最小、明确的 IPC 接口；验证调用来源与参数。渲染层不能传入任意文件路径或执行命令，只能操作固定存档入口。采用限制资源与网络来源的 CSP，禁止任意导航、新窗口和远程脚本；外部链接校验协议和域名后交给系统浏览器。

安卓只申请实际需要的网络、通知及用户选择文件相关能力，不申请通讯录、微信聊天读取或广泛文件访问权限。导入导出使用系统文件选择流程；摘要视为纯文本，不把不可信文本作为 HTML 插入。

游戏资产本地加载，只有用户启用推送后才访问批准的服务端点；网络使用 HTTPS，限制请求长度和超时，不允许未校验的任意 URL。第三方推送会接触发送内容，启用前说明发送哪些事件信息。无统一开发者私钥随包分发。

## 11. 构建与发布

Windows 构建环境需要 Node.js 和所选 Electron/Forge 工具链；Android 另需 Android Studio、兼容的 JDK、SDK 与 Gradle。游戏运行不要求玩家安装 Node.js、Python 或开发服务器。

Vite 生成共用网页资源，使用容器可解析的相对资源引用。Electron 打包本地构建目录，Capacitor 同步同一目录进入 Android 工程。应用不加载开发服务器地址；构建时检查缺失资源和误引用的调试地址。

首版交付 Windows x64 安装包；便携版可后补。安卓交付签名 release APK，安装来源需由用户在系统中允许；debug APK 仅供开发测试，不作为正式发布件。使用同一 applicationId 和签名密钥递增 versionCode，验证覆盖安装后存档保留。妥善备份签名密钥，凭证不提交 Git。Windows 公开分发前评估代码签名及系统信誉提示，不保证未签名程序没有提示。

记录安装包版本、依赖锁文件、资源清单和 SHA-256 校验值。首版采用手动下载安装更新，不实现自动更新服务。构建依赖下载需要网络，安装完成后的核心游戏离线运行。

## 12. 正式工程的实施顺序

1. 以 src/game.js 和 tests/ 中的回归测试为基线，将规则迁入 TypeScript 核心，先保持行为一致，再替换界面入口；旧 demo 目录已移除，不把生成目录作为长期源码目录。
2. 引入 Vite、统一类型与内容配置，建立平台接口，保持浏览器预览可用；区分开发快进与正式旅行配置，发布构建不暴露调试快进。
3. 完成存档协议、迁移、双槽或备份、导入导出、确定性旅行事件与离线结算，覆盖失败恢复测试。
4. 集成 Electron，完成 Windows 本地文件、单实例、安全边界、安装和升级验证。
5. 集成 Capacitor，完成 Android 存档、触屏、返回键、前后台恢复和签名 APK，并做真机断网验证。
6. 增加本机提醒；通过独立试验验证微信候选渠道，再接摘要、凭证和发送队列。渠道验证失败不阻塞单机交付。
7. 加入正式美术与全部首版内容，测量性能、完成双端回归并发布。

每个实施批次都更新相关测试、完成适用验证并创建对应 Git commit。未来文档中的建议接口在实际实现时同步维护，不把方案中的功能标记为已经通过测试。

## 13. 验证与验收

| 编号 | 验证对象 | 必须通过的场景 |
| --- | --- | --- |
| T01 | 核心规则 | 资源不为负、永久道具不重复购买、首次补给只发一次、同趟奖励只领一次 |
| T02 | 离线结算 | 同时间重复结算、跨阶段恢复、时间回拨、时区改变、长时间离线且不自动重复旅行 |
| T03 | 存档容错 | 写入失败、截断 JSON、双槽中断、备份恢复、高版本拒绝覆盖、内容版本迁移 |
| T04 | 跨端转移 | PC 导出到安卓及反向导入、超限和恶意文件拒绝、导入失败不损坏当前进度、导出无凭证 |
| T05 | Windows 包 | 干净机器安装、无开发环境断网启动、单实例、重启恢复、窗口缩放与覆盖升级 |
| T06 | Android 包 | 签名 release APK 安装、飞行模式完整循环、进程终止后恢复、返回键、安全区域、覆盖升级 |
| T07 | 本机通知 | 权限拒绝、取消重排、重复提醒去重、点击后正确结算及安卓省电场景 |
| T08 | 微信推送 | 默认关闭、用户主动配置、真实微信接收、断网补发、限额、无效凭证、未知提交结果与日志脱敏 |
| T09 | 构建和界面 | 类型检查、单元测试、资源引用、正式版无快进、桌面与手机入口可点击、必要资源无外部请求 |

核心测试注入时钟和随机源，平台测试用可模拟失败的存储与发送器，避免等待真实旅行时长。微信使用网络模拟覆盖失败分支，再用测试凭证做真实接收验证；不向自动化日志写 Token。安装、通知和系统生命周期需要打包产物及真机证据，不能仅以单元测试代替。
