## 2. 产品目标与首版边界

交付可以下载安装的 Windows x64 游戏和 Android 签名 release APK。两端共用游戏规则、内容和主要界面，断网也能完成“收钱草 → 买补给 → 装包 → 旅行 → 收信 → 收藏 → 再出发”的循环。

保留已经确认的全画幅小屋与庭院：背包准备行李，地图查看旅途，明信片板浏览图鉴，信箱拆信，小摊购买补给。平时看见的是角色的生活场景，操作时才打开弹窗；余额与设置放在角落。

首版内容按 MVP 范围制作：1 只角色、1 个家园、3 个目的地、9～12 张明信片、3 种食物、2 种永久道具，以及读书、吃饭、睡觉、准备出发等少量日常表现。正式旅行时长和资源节奏通过试玩调整，Demo 快进只用于开发验证。

核心玩法不依赖账号、自建服务器或第三方接口。进度保存在本机，通过文件导出、导入完成手动备份和跨端转移，首版不做自动同步与进度合并。好友、排行榜、付费、复杂装修、实时 AI 内容、其他操作系统和应用商店上架另行规划。

## 3. 系统职责与数据流

采用技术方案确定的 Vite、TypeScript 和原生 HTML/CSS；Windows 使用 Electron 与 Electron Forge，Android 使用 Capacitor。依赖版本在工程化时核查兼容性、写入锁文件，并记录实际构建环境。

| 模块 | 职责 |
| --- | --- |
| 游戏核心 `core` | 状态机、命令校验、资源变化、旅行生成、事件与离线结算；不引用 DOM 或平台 API |
| 内容配置 `content` | 物品、目的地、明信片、事件、概率与平衡参数，统一使用稳定 ID |
| 界面 `ui` | 场景、物品入口、弹窗、输入、角色表现和声音，展示已提交的游戏状态 |
| 平台适配 `platform` | 存储、文件、时钟、生命周期、本机通知和凭证，隔离浏览器、Windows 与 Android 的差异 |
| 通知 `notifications` | 可选事件摘要、发送队列与渠道适配，独立于核心奖励结算 |

一次关键操作遵循：**界面发出命令 → 核心校验并生成候选状态与事件 → 串行保存 → 保存成功后确认操作并刷新界面**。保存失败时保留此前有效状态，提示重试，不显示领取或购买成功。通知在进度持久化后单独处理，网络失败不回滚游戏进度。

正式源码迁入 `src/`，容器代码分别进入 `desktop/` 和 `android/`。保留现有 `demo/` 作为迁移基线，生成目录不作为长期源码目录。

## 4. 核心设计约束

- **旅行结果固定**：确认行李时创建 tripId，确定并保存目的地、奖励和途中事件时间线。重启不重新抽取，同一趟奖励只领取一次。
- **离线推进可重复执行**：启动、恢复前台、执行操作前按时间结算；相同时间重复结算不重复生成事件或奖励。关闭期间不自动开始下一趟，钱草最多成熟一轮。
- **时间保持单调**：使用 UTC 毫秒时间戳；时间回拨时以 `max(now, lastSettledAt)` 结算，接受单机设备向前调时可能提前结束旅行的限制。
- **存档可靠且可迁移**：统一带版本的 JSON 协议，校验数值和内容引用。Windows 使用主文件与备份，Android 使用双槽快照；损坏不静默清空，未知高版本不覆盖。各原生存储方式在对应平台阶段实现。
- **跨端转移明确替换**：导入前校验文件、展示摘要并备份当前进度，经确认后完整替换；导出不含凭证、设备配置或发送队列。Demo 存档通过显式转换入口迁移。
- **画面与交互使用一致坐标**：桌面适配窗口缩放，安卓窄屏重新排布，主要入口至少 44×44 CSS 像素。保留 SVG 结构、绘图层级和点击区域一致性回归检查。
- **平台权限集中管理**：Electron 渲染层仅通过受限接口调用平台能力；安卓使用实际需要的权限和系统文件选择流程。所有必要美术、声音与字体随包分发。

## 6. 美术、内容与通知安排

先保留当前场景作为交互基线，在核心与平台稳定后逐步替换正式资源。首轮挑选一个家园背景、一组角色动作和一张明信片在安卓真机测量首屏、解码、内存和点击响应，再确定资源预算并批量制作，避免全部画完后返工。内容通过配置接入，新增明信片不应修改核心状态机。

本机通知只提醒玩家回来，点击后启动或聚焦游戏并重新结算，不直接发放奖励。安卓接受系统调度带来的非精确提醒；Windows 首版不保证退出进程后提醒。

微信默认关闭，先用固定模板汇总已发生事件。PushPlus 仅是候选，必须验证真实微信到达、绑定、额度与条款后才列为支持渠道。发送凭证放入设备安全存储，不写入源码、日志或导出存档；队列重试、限额与未知提交结果按技术方案执行。应用退出后的定时微信发送不在首版保证范围。

## 7. 验证与交付管理

每个实施批次必须更新相关测试、完成适用验证并创建对应 Git commit。迁移先保持行为一致，再增加能力；发现问题优先补充可复现的回归测试。每次交付记录实际通过的检查、产物及尚未验证的条件。

| 验证层次 | 所需证据 |
| --- | --- |
| 核心与协议 | 注入时钟和随机源的单元测试，状态与内容校验、重复操作、失败恢复和迁移样例 |
| 界面与资源 | 浏览器实测、桌面与手机尺寸截图、SVG 结构与点击坐标检查、资源引用及正式版配置检查 |
| Windows 与 Android | 实际安装包、干净环境与安卓真机结果，断网、进程终止、覆盖升级和双向存档转移记录 |
| 提醒与微信 | 权限、调度、队列失败模拟，以及实际本机提醒和测试微信接收记录；日志不含凭证 |

单元测试不能替代安装、通知和生命周期验证。正式交付包含 Windows x64 安装包、Android 签名 release APK、版本与构建环境记录、资源授权清单、SHA-256 校验值，以及安装、备份、迁移和更新说明。签名密钥妥善备份，不提交 Git；首版采用手动下载安装更新。
